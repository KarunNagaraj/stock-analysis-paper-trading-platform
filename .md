# Stock Analysis & Paper Trading Platform — Project Context

## 1. Project Purpose

A full-stack stock research and paper-trading platform designed for personal learning and resume demonstration.

The application allows users to:

* Search for stocks.
* Screen stocks using fundamental and financial filters.
* View detailed stock information.
* Analyze historical price data using interactive candlestick charts.
* Apply technical indicators.
* Maintain a watchlist.
* Create and manage a simulated trading account.
* Place market, limit, and stop paper-trading orders.
* Track positions, portfolio value, and realized/unrealized P&L.

### Project Principle

Prioritize:

1. Explainability
2. Clear architecture
3. Maintainable code
4. Understanding of data flow
5. Interview-ready implementation

Avoid unnecessary complexity, infrastructure, or abstractions unless they provide a clear learning or architectural benefit.

### Architectural principle

The frontend does not directly access the database or external market-data provider.

The backend owns:

* Business logic
* Data access
* External API integration
* Order execution
* Portfolio calculations
* Validation

The frontend primarily:

* Displays state
* Collects user input
* Calls APIs
* Manages UI state

## 7. Paper Trading Rules

### Supported order types

```text
MARKET
LIMIT
STOP
```

### Order states

```text
PENDING
EXECUTED
CANCELLED
REJECTED
```

### Position accounting

Use weighted-average cost for V1.

```text
Average Cost =
(total cost of existing shares + cost of new shares)
/
(total quantity)
```

### P&L

```text
Unrealized P&L =
Current Market Value - Position Cost

Realized P&L =
Profit/loss from closed positions

Total P&L =
Realized P&L + Unrealized P&L
```

### Portfolio value

```text
Portfolio Value =
Cash Balance + Current Value of Open Positions
```

### Important architectural rule

The frontend must never determine whether an order executed.

```text
Market Data
     ↓
Order Execution Engine
     ↓
Order State
     ↓
Trade
     ↓
Position
     ↓
Account
     ↓
P&L
     ↓
Frontend
```

## 10. Development Method

Features must be implemented end-to-end.

Preferred flow:

```text
Requirement
    ↓
Database changes
    ↓
Backend model/repository
    ↓
Service/business logic
    ↓
Controller
    ↓
API route
    ↓
Frontend API integration
    ↓
Frontend feature
    ↓
Local testing
    ↓
Explain/understand
    ↓
Mark feature complete
```

Cross-cutting concerns should be implemented only to the extent required by the current feature.

Example:

If authentication is required for Watchlist, implement the necessary authentication infrastructure before completing Watchlist rather than building the entire authentication system months earlier.

## 12. Important Design Decisions

1. Use a modular monolith rather than microservices.
2. Organize backend primarily by domain/feature.
3. Separate controllers, services, and repositories.
4. Frontend communicates with backend through REST APIs.
5. Backend owns business logic.
6. Database access is isolated from controllers.
7. External market-data providers are accessed through a market-data service.
8. Start with mock market data where useful, then integrate a real provider.
9. Use weighted-average cost for position accounting.
10. Paper trading is simulation only; no real brokerage execution.
11. The chart is a major application component rather than a decorative visualization.
12. Code should favor clarity over clever abstractions.
13. Every completed feature should be explainable from frontend → backend → database/external service and back.
14. Do not introduce infrastructure such as Redis, Kafka, Kubernetes, or microservices without a concrete requirement.

Updated Project Status / Changes to Original Plan: Features 1–3 are complete, and Feature 4 (Historical Market Data) is now complete. The project uses a deliberately simple architecture appropriate for a personal/resume project rather than an industry-grade market-data platform. The stock universe was changed from the original US examples to a selected NSE equity set: RELIANCE, TCS, INFY, HDFCBANK, ICICIBANK, SBIN, ITC, LT, AXISBANK, and BHARTIARTL. The fundamentals table and stock-details API remain part of the project, but fundamentals are currently empty and can be populated later. For historical market data, instead of building a generic market-data provider abstraction, Python directly downloads NSE CM Bhavcopy files and inserts the required OHLC/volume data into MySQL's simple historical_prices table (stock_id, trading_date, open_price, high_price, low_price, close_price, volume, etc.), with a unique (stock_id, trading_date) constraint. The Python ingestion process is separate from the Node/Express backend and is intended to support both the initial 2024–2026 bulk import and future scheduled daily ingestion. The Node backend exposes historical data through GET /api/stocks/:symbol/history, using the existing repository → service → controller architecture, while the React frontend accesses it through getHistoricalPrices() in stockService.ts. Historical data is now fetched by a dedicated HistoricalPriceChart component rather than making StockDetails.tsx responsible for historical-data/chart logic; StockDetails remains the page-level component that composes the stock information and historical-data component. The original plan's generic “market-data provider”/mock-provider approach has therefore been simplified: NSE Bhavcopy is the historical source, while yfinance is planned later for current/latest market prices. Feature 5 is the next feature and will focus on rendering the fetched historical OHLC data as an interactive candlestick chart using TradingView Lightweight Charts; chart-specific transformation and visualization logic should remain inside the dedicated chart component rather than being added to StockDetails. The originally proposed API path /api/market-data/:symbol/history is no longer the implemented historical endpoint; the current endpoint is /api/stocks/:symbol/history. Avoid introducing unnecessary provider registries, instrument-master tables, adjusted-price pipelines, or other production-grade abstractions unless a concrete feature requires them.
